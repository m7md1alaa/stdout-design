# 0018. Introduce Image & Emoji Resolution as a core module, run between compile and render, with fetch policy owned outside the render boundary

## Status

Proposed

## Context

`packages/core`'s own render pipeline (`orchestrate.ts` → `engine/render.ts`'s `compileTemplate` → `engine/renderer.ts`'s `renderToPixels`/`measureTemplate`) does not fetch external images or extract emoji at all today. This isn't a missing-config problem, it's a missing-step problem:

- `compileTemplate` calls `fromJsx` (from `takumi-js/helpers/jsx`) and returns `{ node, stylesheets }`. Nothing between that and `renderer.render(node, options)` walks `node` for remote `<img src>` / `backgroundImage` / `maskImage` URLs, and nothing calls `extractEmojis`. `orchestrate.ts`'s `prepPipeline` never populates `RenderOptions.images`.
- The native `@takumi-rs/core` `Renderer.render()` — the class our `engine/renderer.ts` calls directly — only ever accepts `images?: Array<ImageSource>` (`{ src, data, cache? }`, pre-fetched bytes only; confirmed against `@takumi-rs/core`'s own `index.d.ts`). It has no fetch mechanism of its own. Fetching, timeout/size limits, an SSRF allowlist, and single-flight dedup all live one layer up, in `@takumi-rs/helpers`'s `prepareImages({ node, sources, fetchCache, fetch, timeout, maxBytes, allowUrl, signal, throwOnError })` and `extractEmojis(node, provider)` — neither of which this codebase calls anywhere (`grep` for `prepareImages`/`extractEmojis` across `packages/core/src` returns nothing but the `fromJsx` import).
- **This gap is asymmetric.** `packages/core/src/og/response.ts`'s `createOgResponse` builds on `takumi-js/response`'s `ImageResponse`, whose `ImageResponseOptions` is `RenderOptions & ResponseInit`, where `RenderOptions` is `takumi-js`'s _managed_ type (`render-Cb_LVX55.d.mts`) — the one that already wraps `prepareImages`/`extractEmojis` internally and accepts `images` as the fetch-capable group form (`ImagesInput`) plus `emoji: EmojiType | "from-font"`. So the production OG route (`apps/web-docs/src/app/og/docs/[...slug]/route.tsx`) already has a working, network-capable image/emoji pipeline underneath it — it's just not exposed, since `OgResponseOptions` (our wrapper type) doesn't list `images` or `emoji` as accepted fields. Meanwhile the studio dev-server preview and CLI batch path — the one built on the raw `Renderer` class — has no pipeline to expose in the first place. Any template with a remote `<img src>`, previewed in the studio or rendered via `stdout-design render` batch, renders with that image unresolved today.
- **Our own type shim is currently wrong about this.** `engine/takumi-types-shim.ts`'s `ImagesOption` declares a group form directly on the native `RenderOptions.images` (`{ sources, fetch, timeout, fetchCache }`), matching `takumi-js`'s _managed_ `ImagesInput` shape, not the real native `@takumi-rs/core` `RenderOptions.images: Array<ImageSource>`. Nothing exercises this today (nothing populates `images` at all), so it's latent, but the moment someone follows the shim's own types and passes `images: { fetch: ... }` straight into `renderer.render()`, the native binding will reject it at runtime the same way the `filter: url(...)` value was rejected earlier — a type that compiles but the native layer doesn't recognize.
- Separately, `RendererConstructor` in the same shim is typed `new () => Renderer` (no arguments), but the real `@takumi-rs/core` `Renderer` constructor takes an optional `RendererOptions` with `cacheMaxBytes` (default 16 MiB — "byte budget shared by every cached resource: decoded images, SVG rasters, parsed stylesheets"). The shim currently makes that budget un-configurable from TypeScript, independent of anything else in this ADR, and should be fixed alongside it since both are the same file.
- **Where the policy question actually lives.** `prepareImages`'s `allowUrl` is the SSRF control — "return false to skip fetching a URL." The one caller with an open, unauthenticated HTTP surface is dev-server's `POST /render` (`packages/dev-server/src/index.ts`): the request body's `props` is validated only against the _template's_ own Zod schema, then flows through `orchestrateRender` unchanged. A template prop like `imageUrl: z.string()` interpolated into `<img src={props.imageUrl}>` means the request body currently controls the fetch target, with nothing between the request and the (currently nonexistent) fetch. Wiring `prepareImages` in without an enforced `allowUrl` would turn "images silently don't work" into "images fetch anything the request body points at" — a regression, not a fix.
- **`studio.config.ts` can hold what the current schema would silently drop.** It's loaded via a real `import()` (`packages/core/src/batch/loaders.ts`), not JSON, so a live function value (`allowUrl: (url) => ...`) is representable in the module. But the loaded object is immediately run through `parseStudioConfig` → `studioConfigSchema.safeParse` (`packages/core/src/shared/config-schema.ts`), and Zod's default `z.object()` behavior strips any key not declared in the schema from `parsed.data`. An `allowUrl` written into `studio.config.ts` today would silently vanish, not just go untyped — the schema needs an explicit, function-permitting field before this can work at all.
- **Interaction with the caches that already exist.** Two caching layers already sit in this pipeline and any image cache has to compose with them, not duplicate them:
  - `RenderCache`'s disk pixel cache (`packages/core/src/cache/render-cache.ts`) is content-addressed by `templateContentHash + propsJSON + width + height + format`, an O(1)-average indexed SQLite lookup + verified disk read. On a hit, `orchestrateRender` returns before `renderToPixels` runs at all — so image fetching is only ever paid on a pixel-cache _miss_ (first render of a given prop set, or any CLI batch run, which by construction starts cold).
  - The native renderer's own decode cache (`cacheMaxBytes`, 16 MiB default) is process-global, living on the `activeRenderer` singleton in `engine/renderer.ts` — the same singleton the file's own comment says exists "purely to reuse the renderer's internal font cache/thread pool." A shared image byte-fetch cache belongs at that same scope for the same reason.
- **Complexity shape.** A batch run's props matrix (`packages/core/src/batch/matrix.ts`'s `expandMatrix`) is exactly the shape where this matters: the same logo/background URL typically repeats across every locale × preset cell. Without a byte-fetch cache, `n` cells referencing `k` distinct images (usually `k ≪ n`) cost `O(n)` network fetches; with a single-flight `fetchCache` shared across the run, it's `O(k)` fetches plus `O(n)` `O(1)`-average cache reads. `prepareImages`'s `fetchCache` is Promise-keyed by URL specifically to also collapse _concurrent_ requesters of the same not-yet-cached URL into one fetch (single-flight) — relevant to dev-server today (genuinely concurrent HTTP requests), and to CLI batch once it's actually concurrent. It currently isn't: `runBatch` (`packages/core/src/batch/batch.ts`) processes cells in a strictly sequential `for...of` loop (`// oxlint-disable eslint/no-await-in-loop`), even though `--concurrency` (default `4`) is parsed all the way from the CLI (`packages/cli/src/index.ts`, `resolver.ts`) into `BatchInput.concurrency` and then never read inside `runBatch`. That's a separate, pre-existing bug, out of scope here — but it's a reason to design `fetchCache` for concurrent dedup now rather than assume batch stays single-threaded.
- **A render that measures then renders pays this cost twice without sharing.** `renderAutoSized` (`engine/renderer.ts`) calls `measureTemplate` then `renderToPixels` on the same compiled node. Once image resolution is wired into both `orchestrateMeasure` and `orchestrateRender`'s shared `prepPipeline`, an auto-sized render would fetch every image twice per call unless the same `fetchCache` instance backs both.
- **A gap this ADR does not close.** None of the three caches (pixel cache, decode cache, fetch-byte cache) key on the bytes actually returned by a remote image URL. If the same URL's upstream content changes, the pixel cache keeps serving the old render until `templateContentHash` or `props` change — there's no cache-busting path. Same posture as ADR-0007's font-fetch-failure fallback: called out explicitly rather than inherited silently, not solved here.

## Decision

- New module `packages/core/src/assets/image-resolver.ts`, sibling to `assets-resolver.ts` (ADR-0007), **not** folded into `resolveAssetsForLocale`. The two operate at different pipeline stages on different keys: `resolveAssetsForLocale` runs _before_ compile, keyed by locale id, producing merged props/fonts/lang. Image resolution runs _after_ compile, keyed by the URLs actually present in the compiled `Node` tree, locale-independent. Collapsing them back into one function recreates the exact "two concerns drifting inside one file" problem ADR-0007 exists to close.
- The new module wraps `extractEmojis` (if an emoji provider is configured) followed by `prepareImages`, called from `orchestrate.ts`'s `prepPipeline` immediately after `compiled` is available (fresh or cache-hit) and before `renderToPixels`/`measureTemplate` are invoked. Its output (`images: ImageSource[]`) is threaded into both call sites' options alongside the existing `fonts`/`fontFamilies`/`lang`, the same way font resolution already flows through that function.
- **Fetch policy (`allowUrl`, `maxBytes`, `timeout`, custom `fetch`, `fetchCache`) is project-level only**, sourced from `studio.config.ts` for the studio/CLI path and from `OgResponseOptions` (set by whoever wires the OG route, not by the request) for the production path — never read from request `props` or template JSX. `allowUrl` defaults to deny-all; a project opts in explicitly. This is a direct consequence of the dev-server finding above: the one open, unauthenticated call site is exactly the one whose "call site" is attacker-influenced, so policy set at that level isn't policy.
- **Fetch data — which URL — stays exactly where it is today: a normal prop / JSX value.** Nothing about this ADR changes how a template writes `<img src={...}>`.
- **`emoji` provider selection is call-site/template-level**, threaded through `OgResponseOptions` and the equivalent studio/CLI render options, with an optional project-level default in `studio.config.ts`. No security implication — a docs card may want `"from-font"` (zero network calls, COLR glyphs), a marketing card may want `"twemoji"` — so no reason to force one project-wide value the way `allowUrl` must be forced.
- One `fetchCache` instance lives for the process lifetime (bounded/LRU-evicting, not the plain unbounded `Map` the upstream docs warn against), constructed once alongside the `activeRenderer` singleton in `engine/renderer.ts` and shared by every `orchestrateRender`/`orchestrateMeasure` call — including the measure-then-render pair inside `renderAutoSized` — so repeated or paired calls don't double-fetch.
- `engine/takumi-types-shim.ts` gets two corrections as prerequisites: `ImagesOption` is retyped to match the real native `RenderOptions.images: Array<ImageSource>` (the fetch-capable group form belongs on `image-resolver.ts`'s own input type, sourced from `@takumi-rs/helpers`'s real `PrepareImagesOptions`/`FetchOptions`, not smuggled into the native renderer's option type); and `RendererConstructor` gains the optional `RendererOptions` (`cacheMaxBytes`) the real constructor already accepts.
- `studioConfigSchema` (`packages/core/src/shared/config-schema.ts`) gets an `images` field whose `allowUrl`/`fetch` members are declared permissively enough (e.g. `z.custom<...>()`) to survive `safeParse` instead of being silently stripped as unrecognized keys.
- `allowUrl` rejections (and other `prepareImages` failures) surface through the same `PropValidationError`-shaped error path dev-server already uses for schema failures, not as a raw fetch exception — so `web-ui`'s existing error-issue rendering (`canvas.tsx`) shows "blocked by allowUrl: `<url>`" instead of a generic renderer stack trace.

## Consequences

**Positive**

- Makes external images and emoji actually work in the studio preview and CLI batch path, where they currently silently don't — closing the asymmetry with the already-working OG response path.
- Closes the SSRF-shaped gap _before_ it becomes reachable: `allowUrl` is enforced from day one of image fetching existing in this pipeline at all, not retrofitted after a template ships a `src` prop into production.
- Turns a batch matrix's `O(n)` external-image fetches into `O(k)` for `k` distinct images, with single-flight concurrent dedup ready for whenever the already-parsed-but-unused `--concurrency` batch flag gets wired up (tracked separately).
- Fixes two independent, currently-latent type-shim bugs (`ImagesOption` shape, `RendererConstructor` arity) as a side effect of touching the same file for the right reason.
- Extends `studioConfigSchema` to actually preserve what a real TS module can already express, instead of silently dropping function-valued keys.

**Negative / risk**

- Default-deny `allowUrl` is a breaking behavior change for any project that assumed (incorrectly, as it happens) that external images already worked and would now start working unrestricted. Needs a clear "blocked by policy, add `images.allowUrl` to `studio.config.ts`" message, not a silent no-op.
- Pixel-cache staleness on remote image content changes is real and explicitly not addressed here — same URL, changed upstream bytes, stale cached render survives until `props`/`templateContentHash` change.
- The decode cache is process-wide, shared by every concurrent render regardless of tenant/template — a large batch run competing for the same `cacheMaxBytes` budget as a concurrent dev-server preview is a noisy-neighbor risk, bounded only by that one number.
- `measureTemplate` gains a network dependency it didn't have before (image intrinsic sizing can affect layout), which changes `/measure`'s latency and failure modes — it was previously a pure layout computation.

## Alternatives Considered

**Let `allowUrl` be a render option passed at the call site, the same tier as `fonts`/`fontFamilies` today.** Rejected: the one caller with an open, unauthenticated HTTP surface (dev-server's `/render`) is exactly the caller whose call-site options are built from request `props`. A policy knob set at that level isn't a policy — it's the thing the policy is supposed to constrain.

**Adopt `takumi-js`'s managed `render()`/`ImageResponse` wrapper for the studio/CLI path too, instead of building a separate resolver on top of the raw `Renderer` class.** Rejected: the managed wrapper bundles `fromJsx` + image/emoji prep + render into one call, with no seam to cache the compiled node independently of the rendered pixels. `orchestrate.ts` deliberately separates those (`CompileCache` vs the pixel cache in `RenderCache`) so repeated renders of the same template+props at different sizes skip recompilation — adopting the managed wrapper would collapse that seam.

**Fold image resolution into `resolveAssetsForLocale` (ADR-0007).** Rejected: different pipeline stage (post-compile vs pre-compile) and different key (URL/content-tree vs locale id). Same reasoning ADR-0007 itself used against keeping fonts and locale-merge in one file.

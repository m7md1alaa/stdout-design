# ADR 0001 — Clean architecture, terminology, and package boundaries for stdout-design

**Status:** accepted

**Scope note:** the system is pre-release with no external consumers yet. Every rename below is applied directly, in place — no aliases, no deprecation warnings, no major-version ceremony, no migration notes. That overhead is for systems with users to protect; this one doesn't have any yet, so the correct terminology and boundaries go in now, once, cleanly.

**Note on process:** the repo currently has a single flat `docs/ADR.md` rather than `docs/adr/000N-slug.md`. That file's content doesn't match this system at all (it documents an unrelated marketing/video-asset product) and `architecture.html` links to it as if it explains "one render pipeline, multiple front doors" — it doesn't. First decision below fixes that. Once this document is accepted, each numbered section should be split into its own `docs/adr/000N-slug.md` per the standard format; it's delivered as one file here for a single review pass.

---

## 1. Retire `docs/ADR.md`; adopt `docs/adr/000N-slug.md` going forward

**Context:** `docs/ADR.md` is dangling — its content belongs to a different product and doesn't back any claim `architecture.html` makes. A single undated, unnumbered file also can't hold multiple independent decisions without becoming a dumping ground.

**Decision:** delete `docs/ADR.md`. Create `docs/adr/`, starting at `0001` (this document). `architecture.html`'s "See ADR.md for the full decision record" link is updated to point at the specific ADR that backs each claim it makes, not a single catch-all file.

---

## 2. Rename Stage A / Stage B to what they actually hold

**Context:** "Stage A" and "Stage B" name cache tiers by pipeline position, not by content. This isn't just prose — it's baked into public, exported identifiers a package consumer has to type: `StageAKeyInput`, `StageBKeyInput`, `StageBEntryInput`, `StageBEntryRow`, `createStageAKey`, `createStageBKey`, `RenderCache.getStageA/setStageA/getStageB/setStageB`, and the SQLite table `stage_b_entries`. Every new contributor has to memorize an arbitrary letter mapping before they can reason about the code, and it's already leaked into `architecture.html`'s section headers, compounding the cost of leaving it as-is.

**Decision:** rename by what each tier stores, not where it sits:

| Old | New |
| --- | --- |
| Stage A / `StageACache` | **Compile Cache** / `CompileCache` — in-memory, holds compiled JSX node trees (`fromJsx` output) |
| Stage B | **Pixel Cache** — disk + SQLite, holds rendered image bytes |
| `StageAKeyInput` | `CompileCacheKeyInput` |
| `StageBKeyInput` / `StageBEntryInput` / `StageBEntryRow` | `PixelCacheKeyInput` / `PixelCacheEntryInput` / `PixelCacheEntryRow` |
| `createStageAKey` / `createStageBKey` | `createCompileCacheKey` / `createPixelCacheKey` |
| `RenderCache.getStageA/setStageA/...` | `RenderCache.getCompiled/setCompiled/...` |
| `RenderCache.getStageB/setStageB` | `RenderCache.getPixels/setPixels` |
| `stage_b_entries` table | `pixel_cache_entries` |

**Consequences:** breaking rename across `core`, `dev-server`, `cli`, and `web-ui`. No aliases, no deprecation window, no major-version ceremony — the system has no external consumers yet, so this is a straight find-and-replace across the monorepo in one commit. `architecture.html` and any in-progress MCP tool schemas that already reference "Stage A/B" get updated in the same change.

## 3. Fix Compile Cache to actually be LRU (behavior bug, not just naming)

**Context:** `stage-a-cache.ts`'s class comment calls it "a pure insertion-order LRU," and its own test suite asserts eviction happens `"strictly in insertion order"` — but `get()` never promotes a hit to the back of the eviction queue. This is FIFO, not LRU. In real `studio dev` traffic, the five templates someone is actively iterating on can be evicted in favor of templates nobody has touched in an hour, purely because they were registered first. The mislabeling has already propagated into `architecture.html` ("in-memory LRU").

**Decision:** `CompileCache.get()` (renamed per §2) moves a hit to most-recently-used position before returning. Update the test that currently documents FIFO behavior to instead assert real LRU behavior (recently-read entries survive eviction under pressure; only genuinely untouched entries are evicted first).

**Consequences:** none externally — this is an internal behavior fix behind an already-thin interface (`get`/`set`/`size`). No public type changes beyond those already made in §2.

## 4. `RenderCache` is the only public seam into caching; sub-components become package-internal

**Context:** `RenderCache` already behaves as a clean orchestrator in the real code — `EvictionCoordinator` doesn't know what a cache entry is, only `RenderCache` touches both `FsStore` and `MetadataStore` together. But nothing currently in `core/src/index.ts` prevents `FsStore`, `MetadataStore`, `EvictionCoordinator`, `ConcurrencyLimiter`, or `CompileCache` from being imported directly by a future consumer (CLI, MCP server, or a third-party integration). If any of them is independently reachable, a future caller can write bytes without going through eviction accounting or cross-process locking — silently reintroducing the exact orphaned-bytes and TOCTOU bugs the split was built to eliminate.

**Decision:** `@stdout-design/core`'s public `exports` map (in `package.json`) exposes only: `RenderCache`, its option/stats types (`RenderCacheOptions`, `CacheStats`), the renamed cache-key types from §2, `compileTemplate`, `renderToPixels`, `measureTemplate`, `renderAutoSized`, `registerFont`, `runBatch`, `loadConfig`, `expandMatrix`, `defineSchema`, `studioConfigSchema`, `zodToJsonSchemaShape`, `ErrorCode`/`logError` and friends, and `StudioConfig`/ `TemplateModule` types — i.e. exactly the interface already documented in `architecture.html`'s "Module Depth" section. Everything under `core/src/node/{fs-store,metadata-store,eviction-coordinator,concurrency-limiter, compile-cache,cache-keys}.ts` is marked internal via subpath restriction in `exports`, so `import { FsStore } from "@stdout-design/core"` fails to resolve for external consumers. Internal cross-file imports within `core` are unaffected.

**Consequences:** the MCP server (Tier 4, per the product plan) and any future front door are structurally forced through `RenderCache`, which is the guarantee the architecture doc's "one render pipeline" claim is actually supposed to buy. Also resolves the duplicate-API smell where both `RenderCache.createStageAKey` and the free `createStageAKey` function were independently importable — only the `RenderCache` static form stays public; the free functions move to internal-only.

## 5. Mark test-only escape hatches as test-only, not peer to the real API

**Context:** `getRenderer` and `resetRenderer` are exported from `renderer.ts` at the same level as `renderToPixels`/`measureTemplate`. `resetRenderer`'s own doc comment describes it as forcing a fresh renderer instance — a test seam, not something application code building on `@stdout-design/core` should call. As written, nothing distinguishes it from the real API to someone skimming the module's exports.

**Decision:** `resetRenderer` and `getRenderer` are renamed to `__resetRendererForTesting` and `__getRendererForTesting` and removed from `@stdout-design/core`'s public `exports` outright. No subpath, no re-export for compatibility. Internal test files reach them via relative import within the package, same as any other internal helper.

**Consequences:** none — nothing in `dev-server`, `cli`, or `web-ui` should have been calling these outside of core's own test suite in the first place, and there's no external consumer to break.

## 6. Disambiguate `TemplateLoader` (dev-server) from `loadTemplate()` (core batch)

**Context:** these are two genuinely different implementations of "get me a template module" — `TemplateLoader` in `dev-server` wraps `vite-node`'s SSR pipeline with explicit module-cache invalidation and hot reload; core's batch path uses a raw `import(pathToFileURL(...))` relying on Bun's native TSX support, with no cache and no reload. Near-identical names invite a future contributor to assume one calls the other, or that they share behavior. They don't: a template that behaves one way under `studio dev` could, in principle, compile differently under `studio render` (different JSX transform, different module resolution), which is a real risk to the "preview equals export" claim, not just a naming annoyance.

**Decision:**

- Core's batch-path function is renamed `loadTemplate()` → `importTemplateForBatch()`, making the mechanism (raw dynamic `import`, no cache) explicit in the name.
- `dev-server`'s `TemplateLoader` class keeps its name (it is, correctly, the more capable of the two — SSR + cache + hot reload) but its doc comment gains one explicit paragraph stating it is _not_ the same code path as `importTemplateForBatch()`, and naming why both exist (dev needs hot reload and hasn't paid a process-startup cost yet; batch is one-shot and Bun's native TSX support is cheaper for that case).
- The top-level pitch in `architecture.html` ("preview equals export by construction") is reworded to state the actual guarantee precisely: both paths ultimately call the same `renderToPixels()`/Takumi step on the same `CompiledTemplate` shape, so **output format and rendering behavior are guaranteed identical**; **module-loading mechanics are not** — that's a known, accepted divergence, not an oversight.

**Consequences:** this ADR does not decide to unify the two loading paths into one — that's a larger change (likely requiring `dev-server` to depend on Bun's loader or batch to depend on `vite-node`) and belongs in its own future ADR if the divergence is ever observed to cause an actual preview/export mismatch in practice. For now, the fix is honesty in the claim, not a rewrite.

## 7. Unify npm scope: retire `@stdout/studio`, adopt `@stdout-design/cli`

**Context:** `@stdout-design/core` and `@stdout/studio` use two different npm scopes for packages in the same monorepo describing themselves as one coherent system. Nothing about the name tells a new developer that `@stdout/studio` is the CLI for `@stdout-design/core`.

**Decision:** the CLI package is renamed `@stdout-design/cli`. The published binary name stays `studio` (via `"bin": { "studio": "..." }` in `package.json`) — package name and executable name are allowed to differ; what's fixed is the scope inconsistency between packages, not the command a developer types.

**Consequences:** none to manage — nothing has been published under `@stdout/studio` to a real audience yet. Rename it directly; no deprecated package, no redirect notice.

## 8. Correct the "devDep used at runtime" contradiction in the dependency graph

**Context:** `architecture.html`'s dependency-graph legend labels `Core -.-> CLI` and `Dev -.-> CLI` as `"dev dependency (used at runtime in monorepo)"` — a contradiction stated in the same breath. This isn't a labeling nitpick; it hides a real ambiguity about what happens when the CLI is installed standalone (outside this monorepo) rather than built via the workspace.

**Decision:** the diagram/legend is corrected to distinguish two real, different relationships:

- **Publish-time dependency** — what ships in the published package's own `package.json` `dependencies` field and is what an external installer actually gets. `@stdout-design/cli` depends on `@stdout-design/core` and `@stdout-design/dev-server` this way — genuinely at runtime, full stop.
- **Workspace build-time reference** — TypeScript project references / workspace protocol links used only so `turbo` can build packages in the right order during local development. These have no bearing on what an external consumer receives.

Both `Core -> CLI` and `Dev -> CLI` are re-labeled as plain runtime dependencies (solid line), since that's what they actually are once published. The workspace-only build-ordering relationship, if worth showing at all, gets its own distinct line style with an honest label — not "devDep."

## 9. `@stdout-design/cli` stays shallow — but that's now a recorded decision, not a default

**Context:** the CLI's own architecture doc labels it "shallow" (interface ≈ implementation) and shows nearly every command as a one-line delegation to `core` or `dev-server`. That shape is a legitimate smell in general — but here it also serves a real purpose: publishing the CLI as its own package means someone who only wants the command-line tool doesn't pull in `vite`, `vite-node`, `@vitejs/plugin-react`, or any of `dev-server`'s transitive dependencies unless they explicitly run `studio dev`.

**Decision:** keep `@stdout-design/cli` as a separate published package. Its shallowness is accepted, not incidental — it exists specifically as an installable, minimal-dependency front door, and its remaining logic (`lib/display.ts`, `lib/prop-parser.ts`, `lib/suggest.ts`) is exactly the CLI-specific concern (argument parsing, typo suggestions, terminal formatting) that has no reason to live inside `core`. This gets recorded explicitly so a future contributor doesn't "fix" it by inlining the CLI into core and forcing every install to carry `vite`.

## 10. Batch pipeline module count — flagged for audit, not resolved here

**Context:** `core/src/batch/` has nine files (`batch.ts`, `loaders.ts`, `manifest.ts`, `matrix.ts`, `naming.ts`, `render-one.ts`, `single.ts`, `types.ts`, `utils.ts`) for one end-to-end concept: "run `studio render`." This has the same shape as the pre-ADR caching subsystem's "bounce across six files to understand one thing" problem, but this document doesn't have visibility into each file's actual contents/cohesion, only names — so no merge decision is made here.

**Decision:** open a follow-up audit (candidate ADR 0002): for each file, confirm it changes along an independent axis from the others (matrix expansion, output naming, and manifest writing are plausibly independent and worth keeping separate; `loaders.ts` + `single.ts` + `render-one.ts` sound, from names alone, like they could be one linear per-row execution path and are the most likely merge candidates). Not accepted or rejected in this ADR — recorded as open.

## 11. Fix `serve.ts`'s monorepo-relative default `rootDir`

**Context:** the dev server's default `rootDir` resolves three directories up into this monorepo's own `examples/` folder (`resolve(import.meta.dir, "../../../examples")`). That default is only correct while running inside this repo. If `@stdout-design/cli`/`dev-server` is ever run from an installed `node_modules` copy in a consumer's own repo without an explicit path argument, this default silently resolves to a path that doesn't exist there.

**Decision:** the published package's default becomes `process.cwd()` — correct behavior for an installed tool run from a consumer's project root. The `examples/` convenience default is moved into a repo-local dev script (e.g. `bun run dev:examples`) that is not part of `dev-server`'s shipped behavior.

## 12. Package consumption guide (non-ADR, but recorded here as a required follow-up doc)

This isn't a reversible-decision ADR item, but it's a direct consequence of §4 and §7 and should exist before the MCP server (a fifth front door) ships. `docs/PACKAGES.md` (new file) states plainly:

- **Just want the CLI?** Install `@stdout-design/cli`. You get `core` and `dev-server` as transitive runtime dependencies automatically; you never need to install or import them yourself.
- **Building your own front door** (MCP server, a custom integration)? Install `@stdout-design/core` directly. Import only what §4 makes public — `RenderCache`, `runBatch`, `compileTemplate`/`renderToPixels`, `loadConfig`, `defineSchema`. Nothing under the cache internals is importable, by design.
- **You should not install `@stdout-design/dev-server` directly** unless you're building an alternative live-preview UI to `web-ui` — it exists to be driven by `@stdout-design/cli`'s `studio dev` command, not consumed standalone.

This should be checked against `docs/PRODUCT.md`, which may already partially cover this — reconcile rather than duplicate if so.

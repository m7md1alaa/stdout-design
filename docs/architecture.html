stdout-design

One render pipeline, multiple front doors. Core owns the Takumi binding. CLI, dev-server, and web-ui are thin clients — preview equals export by construction.

TemplateLoader

Boots a Vite dev server in middleware mode (no HMR). Creates a ViteNodeServer for module transformation and a ViteNodeRunner for execution. importFresh() calls runner.executeFile() — full React JSX + TS pipeline.

Module cache invalidation

Deletes module from ViteNodeRunner.moduleCache by both file URL pathname and raw path. Replaced the old ?t=Date.now() approach which caused memory leaks.

FileWatcher

Uses chokidar to watch templates/ + studio.config.ts. Per-path debounce (200ms) — change to file B never cancels a pending reload for file A. Three event types: "template", "full", "template-error".

SSE push

Hono streamSSE at GET /events. Browser connects via native EventSource (useSSE hook). 15s keepalive. Exponential backoff retry (1s → 15s, max 10 attempts).

Two template loading paths

SSR (dev-server)
  • ViteNodeRunner.executeFile()
  • React JSX transform via @vitejs/plugin-react
  • Explicit per-file cache invalidation
  • Hot reload via FileWatcher + SSE
  • Two-stage cache (Compile + Pixel)
Batch (CLI)
  • Raw import(pathToFileURL(...))
  • Relies on Bun's native TSX support
  • No cache invalidation (process exits)
  • No hot reload — one-shot execution
  • No caching (each render is fresh)

RenderCache Sub-System

The two-stage cache was decomposed from one monolithic class (~400 lines) into six specialized sub-modules. The RenderCache orchestrator preserves the exact public API — no downstream consumer changed.

Implementation

CompileCache — in-memory LRU, configurable max entries (default 100). Tracks content-hash → key index for invalidation. No TTL, no size tracking — cheap enough to recompute.
MetadataStore — SQLite via Kysely ORM. Two tables: pixel_cache_entries (hash, file_name, size, dimensions, content_hash, access times) + cache_totals (single-row counter maintained by SQLite triggers). WAL mode for multi-process safety.
FsStore — atomic file writes via write-file-atomic (safe across devices). On read: checks stat().size + Bun.hash() against stored values. Returns null on corruption — self-healing, never throws.
EvictionCoordinator — debounced (250ms), lock-coordinated via proper-lockfile. Partial sweep evicts LRU entries until under budget; full sweep wipes everything. Lock stale timeout: 10s.
ConcurrencyLimiter — wraps p-limit to cap simultaneous FsStore I/O ops. Prevents RSS spikes from N concurrent large-buffer renders. Unbounded by default (matches pre-split behavior).
cache-keys — SHA-256 truncated: 64 bits (16 hex) for Compile, 128 bits (32 hex) for Pixel. Null-byte delimiters prevent ambiguous concatenation. Single source of truth for key derivation.
Interface is ~10 methods. Implementation spans 6 files totaling ~750 lines — depth ratio ~75:1.
SQLite triggers for running totals

Three triggers (trg_pixel_cache_insert, trg_pixel_cache_delete, trg_pixel_cache_update_size) maintain cache_totals atomically within the same transaction as row changes. No SELECT SUM() on every write.

Lock-coordinated eviction

Advisory file lock (proper-lockfile) ensures only one process runs a sweep at a time. retries: 0 — if another process holds the lock, the current pass is skipped; next write retries. Eliminates TOCTOU race in cross-process file deletion.

Self-healing on corruption

On init: PRAGMA integrity_check — if it fails, the DB file is deleted and recreated fresh. On read: if MetadataStore.getEntry() throws, the metadata store is closed and re-initialized. If FsStore.readVerified() returns null, the stale metadata row is deleted.

Content-addressed with content hash

Each Pixel entry stores a Bun.hash() of the file content alongside the bytes. On read, both stat().size and the content hash are verified — catches same-size bit flips that size-only checks would miss.

Core: one render pipeline, multiple front doors

Every front door (CLI, dev-server, web-ui, future MCP) renders through @stdout-design/core. Preview == export by construction — there is no second renderer to drift. This is the single most important structural decision in the repo, and it's the same principle that keeps react-email's monorepo coherent.
